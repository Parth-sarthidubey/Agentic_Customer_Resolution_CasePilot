CasePilot02
The problem

So why hasn't anyone automated it?

Because the right answer depends on facts nobody has gathered yet, and the systems that hold them can say no.

Rules engines

Break the moment reality deviates. A rule cannot tell “stock exists” from “stock exists, but it arrives three days after the birthday.”

Chatbots

Explain the refund policy beautifully. Cannot issue the refund. The work still lands on a human, just later and with more typing.

One big LLM call

Cannot check its own work, cannot recover when an action is refused, and will cheerfully tell a customer their money is on the way when nothing posted.

The hard part isn't answering. It's finding out what's true, acting on it, and being able to show that it worked.

CasePilot06
Under the hood

Five specialists, one state machine

Only one thing writes

The Resolver proposes. An Executor is the single code path allowed to change anything, and it runs typed actions only.

The gate is code

Windows, balances, stock, delivery dates. Arithmetic, not judgement, so a prompt cannot talk it into a bigger refund.

Then we check

A verifier reads the company's own database back and compares it to what the plan promised. Disagreement reopens the case.

Knowing when to stop

Two of our eight demo cases end without acting at all. One escalates a suspicious claim with the evidence attached. One stops and asks a question.

Both are the correct outcome. An agent that always acts is a liability.

The verifier runs on every case, not just the eight we demo. If the ledger disagrees with the plan, the case goes back to planning instead of closing.

Where the line is

The enterprise systems are simulated, but they behave: they enforce constraints, refuse actions and keep state. Swapping in real APIs touches one file. Nothing in the agent layer knows it's a sandbox.

Built for weak models

Typed contracts, a code gate and objective checks mean correctness doesn't depend on the model being clever. It runs on free tiers.
